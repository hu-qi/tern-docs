# 生命周期与重新加载 {#lifecycle-and-reload}

插件在运行它们的进程启动时加载，并在其文件夹发生变化或有人请求时整体重新加载。重新加载会替换该上下文中的每个 VM；运行中的 block 通过已保存的状态延续，运行中的 lens 捕获则在开始的地方结束。本页说明事件发生的顺序、什么会触发重新加载，以及什么能在重新加载或守护进程重启后存续。

## 加载 {#loading}

两个半区都始于对插件文件夹的同一次扫描
（[包与清单](packages.md#directories)）：包按 id 排序，问题项被搁置，被设置项关闭的 id 标记为 Disabled。

**Host 半区** 在会话守护进程启动时加载，早于其恢复已保存的面板，因此恢复的 block 能找到自己的 block 类型。没有守护进程、自行运行面板的窗口在创建第一个面板时加载它们。每个获准的、带有 `host` 入口的包都会获得一个工作线程，由它创建 VM 并在 2 s 的 host 预算内运行入口；所有工作线程同时启动，host 等待每一个报告结果。入口抛出错误、或让已声明的 block 或 lens 未定义的插件为 Failed；其他插件正常加载。

**Window 半区** 在创建窗口时加载，位于 Tern 自身的样式表之后、键位映射首次应用之前。在窗口的 UI 线程上，按 id 顺序，每个获准的包先安装其清单样式，然后在 50 ms 的 window 预算内运行其 `window` 入口。入口失败会弹出提示“插件 *name* 加载失败”，并附上错误的第一行，同时在该窗口中将该插件标记为 Failed。所有入口运行完毕后，窗口读取它们注册的内容：命令面板行、键位映射的插件层、chrome 格式化器与 `tern.css` 样式表。

**`window_start`** 每个窗口每个插件运行一次，在窗口的会话稳定之后（已恢复或刚刚启动），因此工作区脚本能看到它正在添加到的标签页。参见[布局与工作区](../guides/layout.md)。

凡插件轮流参与之处（覆盖、路由、chrome 格式化器、`spawn` 过滤器、lens 认领），顺序都是插件 id 顺序。

## Catalog 与状态 {#the-catalog-and-statuses}

每个半区都为每个插件维护自己的状态：

| 来源 | 报告的状态 |
| --- | --- |
| Host catalog | host 入口的 Ready、Disabled 或 Failed。没有 host 入口的插件只要设置允许，在这里就是 Ready。 |
| 窗口 | 该窗口中 window 入口的 Ready、Disabled 或 Failed。 |

host 的 catalog 就是它发送给窗口的内容（参见
[架构](architecture.md#the-catalog)），也是 `tern plugin list` 打印的内容：运行中守护进程的 catalog，或者在没有守护进程时，未运行任何插件而直接读取的文件夹（每个获准的包都是 Ready）。因此，失败的 window 入口不会在 `tern plugin list` 中显示为 Failed。偏好设置 › 插件 对每个本地插件显示 host 与窗口状态中较差的一个，并在各 host 名称下以只读方式列出所附着的远程 host 的插件。

每当 host 的 catalog 变化（窗口附着时，以及发生使其变化的重新加载之后），且其中包含问题项或 Failed 插件时，窗口会显示一条提示：“1 个插件存在问题”或“*N* 个插件存在问题”，并在下方附上第一条错误。

## 监视 {#watching}

插件文件夹以及其外的每个包目录（`.path` 链接与符号链接的目标）都会被监视变化：

| 平台 | 机制 |
| --- | --- |
| macOS | FSEvents，递归 |
| Linux | inotify，每个目录一个监视（包目录最多 8 层深） |
| Windows | `ReadDirectoryChangesW`，递归 |
| iOS，以及监视未生效之处 | 每 2 s 轮询一次目录树指纹（路径、大小、修改时间；8 层，10,000 个条目） |

未生效的监视（网络卷，或 Linux 用完 inotify 监视数量）会回退到轮询。变更在 300 ms 内批量处理。任何变更都会重新加载该监视上下文中的所有插件，而不只是发生变化的那个包。

守护进程与每个窗口各自独立监视：守护进程重新加载 host 半区，窗口重新加载其 window 半区。

## 重新加载 {#reloading}

| 触发方式 | Host 半区 | Window 半区 |
| --- | --- | --- |
| 被监视文件夹中的一次变化 | 守护进程（或没有守护进程时运行面板的窗口）重新加载；若 catalog 变化，守护进程会把它发送给每个窗口 | 机器上的每个窗口根据自己的监视重新加载 |
| `tern plugin reload` | 守护进程重新加载并以自己的 catalog 作答，同时也发送给每个窗口 | 本机的窗口在收到其守护进程的 catalog 时重新加载 |
| `tern plugin reload ID` | 同 `tern plugin reload`，但仅针对插件 `ID`；其他插件继续运行 | 本机的窗口仅重新加载插件 `ID` |
| `tern plugin install`、`remove`、`link`、`unlink` | 变更之后同 `tern plugin reload` | 同 `tern plugin reload` |
| 命令面板：重新加载插件 | 窗口所附着的每个 host 都重新加载，包括远程 host；没有守护进程的窗口重新加载自己的运行时 | 该窗口重新加载 |
| 偏好设置 › 插件：开关、重新加载、安装… | 同命令面板命令 | 该窗口重新加载 |

`tern plugin reload` 需要运行中的守护进程（否则报 `no daemon running`）。会修改状态的动词在没有守护进程时也能工作，并打印
`no daemon running; changes apply at next start`。参见
[命令行](../reference/cli.md)。

一次编辑通常会让窗口重新加载两次：一次来自其自身的监视，一次在其守护进程的新 catalog 到达时。若某次窗口重新加载的加载失败与上一次加载完全相同，则不会再次弹出提示；catalog 提示仅在 catalog 变化时出现，因此损坏的插件每次变更只报告一次，而不是每次重新加载都报告一次。

在窗口处理器运行期间请求的重新加载（来自定时器，或来自编辑插件文件夹的命令）会在该处理器返回后执行。

## 重新加载后仍然存续的内容 {#what-survives-a-reload}

**Host 半区。** 旧的工作线程退场，新的工作线程从当前文件夹与设置启动。

| 事物 | host 重新加载之后 |
| --- | --- |
| 运行中的 block | 迁移到新的工作线程并重新启动：`init(cx, args, saved)` 以 `save` 上次返回的状态运行（类型没有 `save` 的 block 则为 `nil`）。面板保留；其视图被重建。 |
| 类型已不存在的 block | 插件被移除、禁用或失败，或者该 block 已从清单中删除：该 block 以 `no block type KIND on this host` 结束，退出状态为 1。 |
| 运行中的 lens 捕获 | 在旧的工作线程上、以旧代码完成；旧工作线程在最后一个捕获完成后退出。新命令交给新的工作线程。 |
| 已完成的 lens 捕获 | 其 Lua 状态随旧 VM 一起消失；来自此类 block 的下一个事件会在新的工作线程上重建它（[见下文](#lens-rehydration)）。 |
| 钩子、`spawn` 过滤器、定时器、待处理的进程与 fetch 回调 | 随旧 VM 结束；新入口注册自己的。 |
| 因预算耗尽而暂停的钩子 | 立即再次运行：VM 是新的。 |
| `tern.kv`、数据文件夹中的文件 | 不变。 |

**Window 半区。** 窗口丢弃每个插件 VM 并重新构建它们。

| 事物 | window 重新加载之后 |
| --- | --- |
| Lua 状态、注册项 | 消失；入口再次运行并重新注册。 |
| 插件样式表 | 移除 `plugin:local:*` 样式表并重新安装。 |
| 键位映射、命令面板行、格式化器 | 根据新的注册项重建。 |
| `window_start` | 仅对尚未在该窗口运行过它的插件运行：新添加或新启用的插件会运行它，已经运行过的则不会。 |
| 因预算耗尽而暂停的钩子 | 立即再次运行。 |

window 半区在重新加载之间所需的任何内容都应放在 `tern.kv` 或文件中；block 所需的任何内容都应放在其 `save` 结果中。

## 守护进程重启与升级 {#daemon-restart-and-upgrade}

**重启。** 守护进程启动时如果发现某个已停止的守护进程（退出、崩溃或机器重启）的状态文件，它会先加载插件，然后恢复已保存的面板。Shell 以登录 shell 的形式恢复；正在运行 agent CLI（`claude`、`codex`、`omp` 等）、终端编辑器、监视器或分页器的 shell 会在其第一个提示符处重新运行该命令行，报告过 id 的 agent 会话则恢复。其他内容（构建、服务器、脚本）不再运行。插件 block 以相同的 block 类型恢复，从
`save` 上次返回的状态启动，保持上次的尺寸，屏幕为空白。block 视图之外的任何内容都不会保留，block 也绝不会被恢复为 shell。如果 host 上不再有 Ready 插件定义该 block 类型，该面板不会被恢复（守护进程记录 `cannot restore plugin block`）。恢复因内部错误（panic）而失败的面板同样被略过，其他面板正常恢复；无法从保存的布局中恢复某个 block 的窗口会将它排除在分割布局之外，并在通知中指明它。

**原地升级（Unix）。** 升级会把守护进程交给新构建，而不结束任何程序：shell 保留其伪终端、屏幕与回滚缓冲。插件 block 没有伪终端：插件在交接前停止，最后一次保存的状态被保留，新守护进程像恢复时那样从该状态重新启动每个 block。工作线程上的 lens 状态不会存续。

编写 `save` 时，应使其结果足以重建 block。参见
[block](../guides/blocks.md)。

## Lens 重建 {#lens-rehydration}

Lens 状态只存在于工作线程的 VM 中，每个插件保留最近 256 次捕获。lens block 的寿命长于它：在重新加载、守护进程重启或升级之后，或者一旦该捕获被逐出，block 仍保留其命令行、工作目录、原始输出、宽度与退出状态。

当这样的 block 发送事件（点击带有动作的节点、选择、切换）时，host 把该记录连同事件一起交给工作线程。工作线程再次用其插件的 `match` glob 认领该命令；如果仍然认领，它运行 `open`，然后按 block 的宽度重放已保存输出的每一行并逐行调用 `line`，命令已结束时调用 `finish`，之后调用该事件的处理器，并发送新的视图。如果 glob 不再认领该命令，则不运行任何内容。

重建会重新运行处理器，包括它们具有的任何副作用（提示、进程、文件写入）。应让 `open`、`line` 与 `finish` 不含只应发生一次的副作用。参见[命令 lens](../guides/lenses.md)。
